## 1. 背景与目标

### 现状

- 生产环境（Oracle Cloud 服务器）的 Web 容器 `quant-web` 通过 `DATABASE_URL` 直连 **Supabase PostgreSQL Session Pooler**（`aws-0-ap-southeast-1.pooler.supabase.com:5432`）
- Supabase 免费 / 入门计划 **5GB 传输流量（egress）限制**：调度器每 15s tick、任务列表每 5s 轮询、AI 解读大字段读取都消耗该配额。Pro/Team 为 250GB included
- 开发环境（本地 Windows）使用独立的 Docker 本地 PostgreSQL（`web/docker-compose.dev.yml` 中 `db` 服务，`127.0.0.1:5432`），与生产完全隔离
- 业务 Schema：`quant` schema，9 张表，`SCHEMA_VERSION=1`（当前），单文件 `schema.sql` 幂等管理
- **版本同步保护**：`schema.sql` 末尾版本号与 `web/src/lib/db.ts` 的 `SCHEMA_VERSION` 必须一致，不一致时应用拒绝启动（既有机制）
- **版本升级**：切换 commit 中 `SCHEMA_VERSION` 由 1 → 2（新增角色授权块），与切换同一维护窗口发布（见 6.2）
- Schema 无任何 Supabase 专有特性（无 RLS、realtime、storage、triggers、functions、auth.users 引用）
- 自动部署：push master 触发 `.github/workflows/deploy-oracle.yml` → SSH 执行 `/home/ubuntu/ops/deploy-quant.sh` → `docker compose -f docker-compose.oracle.yml up -d --build`

### 目标

1. **新增同机自建 PostgreSQL**（`quant-db`，PostgreSQL 16），与 `quant-web` 同机部署，Docker 内部网络
2. **生产切到自建库**，消除 Supabase 传输配额与外部依赖；同时优化分页/增量轮询，避免把流量问题转成同机负载问题（见 4.9）
3. **自建库仅线上环境可达**：不暴露端口、独立 internal 网络；**开发机永不直连生产库**
4. 应用以**非超级用户**运行；角色分离
5. 提供可回滚的迁移（明确 RPO/RTO）、可靠备份与恢复演练

## 4. 详细设计

### 4.1 docker-compose：quant-db 独立 override 服务

主 compose 不含 quant-db。切换时叠加：

```bash
# Oracle 版
docker compose -f docker-compose.oracle.yml -f docker-compose.oracle.db.yml up -d
# 通用版
docker compose -f docker-compose.yml -f docker-compose.db.yml up -d
```

`docker-compose.oracle.db.yml` 要点：

```yaml
services:
  quant-db:
    image: postgres:16-bookworm
    restart: unless-stopped
    environment:
      POSTGRES_DB: quant
      POSTGRES_USER: quant_owner          # 容器内超级用户仅作 DDL/setup
      POSTGRES_PASSWORD: "${PG_OWNER_PASSWORD:?PG_OWNER_PASSWORD must be set}"
      TZ: Asia/Shanghai
    volumes:
      - /opt/docker/quant/db-data:/var/lib/postgresql/data   # 宿主机目录
    networks: [internal]                  # 只加入 internal，不暴露
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "quant_owner", "-d", "quant"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 30s

  quant-web:
    environment:
      DATABASE_URL: "postgresql://quant_app:${PG_APP_PASSWORD:?PG_APP_PASSWORD must be set}@quant-db:5432/quant"
      DATABASE_SSL_MODE: "disable"
    networks: [default, internal]         # 能访问 DB 同时保留出网

networks:
  internal:
    internal: true
```

要点：
- **不暴露端口**；quant-db 只加入 `internal` 网络 → 只有同 compose 项目、且显式加入 internal 的服务能连
- **无 `depends_on` 健康门禁**：quant-web 启动不依赖 quant-db 健康 → 回滚到 Supabase 时不受 quant-db 状态阻塞。应用层 pg 连接池有 `connectionTimeoutMillis` 与启动时 schema 校验失败会报错（可加启动重试，见 4.10 可选）
- 角色：`quant_owner`（setup/DDL）、`quant_app`（应用连接，DML）、`quant_backup`（pg_dump 只读）
- `quant_app`/`quant_backup` 不再由 entrypoint 脚本直接执行 DDL；统一由显式的 `npm run db:setup` 创建并授权

### 4.2 SSL 判断逻辑改造

现状代码按主机名判断 SSL：
```js
const local = hostname === "localhost" || hostname === "127.0.0.1" || hostname === "::1";
const ssl = local && !servername ? false : { rejectUnauthorized: ... };
```
`quant-db` 主机名不在白名单 → 会尝试 TLS，而自建 PG 无 TLS → 失败。

改造（4 处：`db.ts` + 3 个脚本）：
```js
const sslDisabled = process.env.DATABASE_SSL_MODE === "disable";   // 或 ${prefix}_SSL_MODE
const ssl = sslDisabled ? false : local && !servername ? false : { ...原逻辑... };
```
向后兼容：未设置时行为不变。`sync-prod-to-local.mjs` 的 `sslFor()` 读 `${prefix}_SSL_MODE`（PROD_SSL_MODE / LOCAL_SSL_MODE）。

### 4.3 数据迁移（Supabase → 自建库）

#### 4.3.1 前置：停写窗口（快照一致性）

迁移必须在**源库（Supabase）停写**状态下进行：

1. **停掉线上 web 容器**（调度器与 Web 写入随停）：
   ```bash
   docker compose -f docker-compose.oracle.yml stop quant-web
   ```
2. 确认无运行中任务：登出后再 `docker compose ps`；若担心 Python 侧残留，`docker compose stop quant-web` 已覆盖（Python 任务由 web 子进程启动）
3. 停写窗口内完成 4.3.2–4.3.5；窗口长度 = 分钟级

> 源库逐表普通 SELECT、无跨表事务快照——因此**必须停写**，否则任务/日志/持仓/配置可能遗漏且跨表不一致。

#### 4.3.2 启动 quant-db 并初始化

```bash
cd /opt/docker/quant/quant-python/quant-python
# .env 需先有 PG_OWNER_PASSWORD / PG_APP_PASSWORD / PG_BACKUP_PASSWORD
docker compose -f docker-compose.oracle.yml -f docker-compose.oracle.db.yml \
  up -d --wait --wait-timeout 120 quant-db
```

`--wait` 会阻塞到 healthcheck 通过；仅查看 `docker compose ps` 不算等待。

#### 4.3.3 建表 / 4.3.4 同步 / 4.3.5 验证（一次性迁移容器）

**quant-web 已被停止，无法 `exec`；且旧容器不在 internal 网络。改用 `docker compose run --rm` 拉起一次性迁移容器**（用 quant-web 镜像，叠加 override 获得 internal 网络，命令行 -e 覆盖 env，跑完即删）。

```bash
# 0) 从 .env 安全提取所需键：Compose 会读 .env 做 YAML 插值，但不会导出给 shell。
#    ⚠ 勿用 `set -a; . ./.env` —— dotenv 非 shell 语法，Webhook/Token/密码中的
#    $()、反引号、分号、空格可能解析失败甚至被命令执行。用 sed 只取键值：
get_env() {
  sed -n "s/^[[:space:]]*$1[[:space:]]*=[[:space:]]*\([^#[:space:]]*\).*/\1/p" ./.env | tail -n1
}
PG_OWNER_PASSWORD="$(get_env PG_OWNER_PASSWORD)"
PG_APP_PASSWORD="$(get_env PG_APP_PASSWORD)"
PG_BACKUP_PASSWORD="$(get_env PG_BACKUP_PASSWORD)"
: "${PG_OWNER_PASSWORD:?PG_OWNER_PASSWORD 未在 .env 中定义}"
: "${PG_APP_PASSWORD:?PG_APP_PASSWORD 未在 .env 中定义}"
: "${PG_BACKUP_PASSWORD:?PG_BACKUP_PASSWORD 未在 .env 中定义}"

# 通用前缀：R=run --rm 迁移容器
RUN_DB="docker compose -f docker-compose.oracle.yml -f docker-compose.oracle.db.yml run --rm"

# URL 编码小工具（避免手工转义）
enc() { python3 -c 'import urllib.parse,sys;print(urllib.parse.quote(sys.argv[1]))' "$1"; }
OWNER_URL="postgresql://quant_owner:$(enc "$PG_OWNER_PASSWORD")@quant-db:5432/quant"
APP_URL="postgresql://quant_app:$(enc "$PG_APP_PASSWORD")@quant-db:5432/quant"
PROD_URL="postgresql://postgres.qutqrxicwrnorvujdrvp:<URL编码密码>@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres"

# 1) 建角色/建表：所有生产 DDL 统一经幂等 db:setup
$RUN_DB \
  -e DATABASE_URL="$OWNER_URL" \
  -e DATABASE_SSL_MODE=disable \
  -e QUANT_SETUP_ROLES=1 \
  -e PG_APP_PASSWORD="$PG_APP_PASSWORD" \
  -e PG_BACKUP_PASSWORD="$PG_BACKUP_PASSWORD" \
  quant-web npm run db:setup

# 2) 同步：PROD=Supabase 源，LOCAL=quant-db 目标
# 两个门禁都必须严格等于 1；目标主机必须精确为 quant-db，其他远程目标直接拒绝。
$RUN_DB \
  -e PROD_DATABASE_URL="$PROD_URL" \
  -e LOCAL_DATABASE_URL="$OWNER_URL" \
  -e LOCAL_SSL_MODE=disable \
  -e QUANT_ALLOW_REMOTE_SYNC=1 \
  -e QUANT_ALLOW_PRODUCTION_CUTOVER=1 \
  quant-web npm run db:sync-from-prod

# 3) 验证：以应用同权角色 quant_app 指向 quant-db
$RUN_DB -e DATABASE_URL="$APP_URL" -e DATABASE_SSL_MODE=disable quant-web npm run db:verify
```

注意：
- `run --rm` 用 override 里的 `internal` 网络 + 目标 env；不依赖被停止的旧容器
- `LOCAL_SSL_MODE=disable`（sync 读 `${prefix}_SSL_MODE`）；PROD 侧保持 TLS 默认
- 生产目标门禁要求 `QUANT_ALLOW_PRODUCTION_CUTOVER=1` 且目标精确为 `quant-db:5432/quant`；本地目标只允许 `loopback:5432/quant`，明确拒绝 `127.0.0.1:15432` 生产 relay；同步连接串禁止查询参数/片段，防止 `host`/`port` 覆盖绕过门禁
- 密码 URL 编码（`@`/`:` 必须转义，用 `enc()` 避免手误）
- 脚本逻辑：db:setup 幂等建表；sync 对 `quant-db` 只校验 schema 版本，不执行 DDL，然后在事务内完成目标清空、逐表复制和序列重置；verify = 以 quant_app 校验行数/序列/事务往返
- 反例：v1 用 `docker compose exec quant-web npm run db:verify`（读 Supabase 且容器已停）→ 既跑不了又"验了旧库"。必须一次性容器 + 显式 -e 指向 quant-db

### 4.4 切换 DATABASE_URL（显式、可回滚）

切换 = **把部署模式开关 DB_MODE 设为 selfhost**（deploy-quant.sh 永久叠加 db override）并把 .env 指向自建库：

```bash
# .env 里设置（服务器 /opt/docker/quant/quant-python/quant-python/.env 或 \$COMPOSE_DIR/.env）：
#    DATABASE_URL=postgresql://quant_app:<URL编码密码>@quant-db:5432/quant
#    DATABASE_SSL_MODE=disable
#    DB_MODE=selfhost          ← 关键：此后每次自动部署都叠加 db override
#    PG_OWNER_PASSWORD=...  PG_APP_PASSWORD=...  PG_BACKUP_PASSWORD=...

# 按 6.2 预构建并完成迁移后，首次手动切换只启动已验证镜像：
docker compose -f docker-compose.oracle.yml -f docker-compose.oracle.db.yml \
  up -d --no-build quant-web
```

验证：页面任务列表/数据源/定时任务正常；`db:verify` 通过。

> 若服务器 deploy-quant.sh 未更新为含 DB_MODE 分支的版本，**不要依赖"自动部署会帮你带上 override"**——必须先同步脚本（见 6.2 Step 1），否则下一次发布即断库。

### 4.5 备份方案（在线逻辑备份为主）

自建库无托管备份。**主备份 = 每日在线逻辑备份（pg_dump）**，不停数据库容器、单次一致性快照。
完整脚本为了同时打包应用目录，会在 Web 原本运行时短暂停止 Web；若 `DEPLOY_PAUSED=1` 则整轮跳过，
且绝不会把维护前已停止的 Web 意外启动。
完整可运行脚本见 `docs/DEPLOY-ORACLE.md` §8.3 `backup-quant.sh`（独立备份目录、锁、fail-fast、
上传失败不清本地、14 天清理）。要点：**dump 输出重定向到宿主机**（勿写容器内 /tmp，宿主机取不到）：

```bash
# 每日 03:00（cron 调用 backup-quant.sh，以下为片段）
docker compose -f docker-compose.oracle.yml -f docker-compose.oracle.db.yml \
  exec -T quant-db env PGPASSWORD="$PG_BACKUP_PASSWORD" \
  pg_dump -U quant_backup -h 127.0.0.1 -d quant --format=custom --no-owner --no-acl \
  > "$HOME/quant-backups/quant-db_$(date +%Y%m%d_%H%M%S).dump"
```

- **14 天保留**：rclone `delete --min-age 14d`（现有脚本该行被注释，需启用）
- **可靠性要求**：备份脚本需 fail-fast（`set -euo pipefail`）、rclone 上传失败**不得删除本地备份**、失败告警；恢复演练见 7.3
- 物理数据目录 tar 备份仅作**辅助**：需确认 PG 已干净停止、保留权限、同大版本（16）恢复；不作为每日基线
- 一致性说明：逻辑备份天然一致；完整脚本最多短暂停 Web 一次，并恢复到原运行状态

> 备份用 `quant_backup` 只读角色；恢复必须在停写窗口内由 `quant_owner` 执行 data-only 灌入。
> 应用角色 `quant_app` 无备份管理或 schema DDL 权限。

### 4.6 回滚方案（区分应用回滚与数据库回滚）

**两类回滚分开设计：**

**A. 应用版本回滚**（代码出问题，DB 不回退）：
- **SCHEMA_VERSION 硬约束**：代码版本必须与 DB schema 版本匹配，否则 `validateSchema` 拒绝启动。
  切换后 DB 为 v2（含授权块）→ **不可回退到 v1 代码**（v1 期望 v1 schema）。
- 应用回滚 = 在本功能 PR 内部的 v2 兼容代码间回退（修 bug 不降版本），或走 B 恢复 v1 栈。
- 完整回退到 v1 栈 = **必须走 B 的数据库回滚 + 同时把应用切回 v1 代码 + Supabase 保持 v1 schema**；
  三者版本必须一致（v1 代码 + v1 schema 的 Supabase）。

**B. 数据库回滚**（自建库出问题，切回 Supabase）：
- **先选分支，不能混用**：切回 v2 后 Supabase 会升级为 schema v2，之后不能再用 v1 镜像；完整回退
  v1 则必须保持 Supabase v1，不得先执行 v2 `db:setup`。
- **数据事实**：迁移 = 全量复制（Supabase → quant-db）；迁移前停写、迁移后 Supabase 不再被写入
  （单调度器），因此 **Supabase 中就是迁移时刻的完整数据快照**——回滚不需要数据搬移，也不需要
  DROP/TRUNCATE/pg_restore（符合「生产 DDL 只能走幂等 db:setup」硬规则）。

**B1. 保留 v2 代码，数据库切回 Supabase（推荐的快速服务恢复路径）**：

1. 先设置 `DEPLOY_PAUSED=1`，再按 6.2 Step 2 等待获取 `$HOME/quant-maintenance.lock` 并复核暂停值，然后停止
   selfhost `quant-web`；记录当前 v2 commit SHA。
2. 使用当前 v2 镜像和 Supabase owner 连接串执行一次幂等 `db:setup`，把 Supabase 从 v1 升到 v2：
   ```bash
   docker compose -f docker-compose.oracle.yml run --rm \
     -e DATABASE_URL="<Supabase owner URL>" quant-web npm run db:setup
   ```
3. `db:setup` 成功后才修改 `.env`：DATABASE_URL 指回 Supabase、删除 `DATABASE_SSL_MODE`、
   设置 `DB_MODE=legacy`。
4. 启动 v2 Web：`docker compose -f docker-compose.oracle.yml up -d --no-build quant-web`。
5. 使用同一个 Supabase URL 运行 `db:verify`，页面抽查通过后再设 `DEPLOY_PAUSED=0` 并释放维护锁。

**B2. 完整回退到 v1 代码 + Supabase v1**：

1. 先设置 `DEPLOY_PAUSED=1`，再按 6.2 Step 2 等待获取维护锁并复核暂停值，停止 selfhost `quant-web`；
   **不得**对 Supabase 执行 v2 `db:setup`。
2. 把预留镜像恢复为 Compose 使用的标签：
   `docker image tag quant-web:pre-cutover-v1 quant-web:latest`。
3. `.env` 恢复 Supabase URL、删除 `DATABASE_SSL_MODE`、设置 `DB_MODE=legacy`。
4. `docker compose -f docker-compose.oracle.yml up -d --no-build quant-web`，以 v1 `db:verify` 校验。
5. 保持 `DEPLOY_PAUSED=1`，直到 master 已回退/修复为 v1 兼容 commit；否则解除暂停会再次部署 v2。
- **观察期新增数据**（quant-db 中产生的任务/日志/持仓/配置）：回滚后这些数据**留在 quant-db**，
  **不会自动同步到 Supabase**。这是**数据库回滚的 RPO**（恢复点目标），默认 ≤1 周（观察期长度），
  **需要业务显式接受**。如需保留，回滚前 `pg_dump` 自建库留档。观察期可缩短到数小时以降低 RPO，
  但无法为零（切换后自建库与 Supabase 处于不同时间点）
- **独立灾备分支**（quant-db 卷损坏、容器无法启动）：同上——Supabase 仍是迁移时刻快照，直接翻回
  连接串即可恢复服务；quant-db 后续重建后如需补数据，再从 R2 最新 dump 恢复到新卷（见 7.3 演练，
  恢复用全新卷 + 幂等 db:setup + data-only pg_restore（见 8.1，先建 schema 再灌数据），不做任何生产库破坏性操作）
- **观察期策略**：切换后 Supabase 项目暂停/降级但**不删除**至少 1 周；观察期新增数据如需归档，
  每日逻辑备份自建库 + 回滚前手动 pg_dump

**单调度器约束**：advisory lock（`db.ts: SCHEDULER_LOCK_KEY`）只在**各自数据库内**有效。两个库同时有调度器 = 双调度器并发跑任务。规则：
- 同一时刻**只有一个 web 实例连一个库并跑调度器**
- 切换前：Supabase 上的 web 是唯一调度器（停写窗口已停）
- 切换后：quant-db 上的 web 是唯一调度器；本地开发永远 `SCHEDULER_DISABLED=1`
- 回滚 B 期间：先停自建库 web，再启 Supabase web，杜绝重叠

### 4.7 开发环境（删除直连生产库设计）

| 项 | 说明 |
|----|------|
| 本地开发容器 `db` | 不变，`127.0.0.1:5432`，完全独立 |
| **开发机直连生产库** | **已删除**：不提供 SSH 隧道、不提供生产库公网/局域网可达路径。生产库仅 internal 网络 |
| 本地开发需要生产数据做联调 | 用**离线导出**：服务器每日备份产生的 dump 文件，通过 scp/其他通道取回后 `pg_restore` 到本地 `db` 容器；开发机**只接触备份文件，不直连生产库** |
| `db:sync-from-prod` | 该脚本的 prod→local 语义保留，但**仅在服务器本机**（或能同时达两库的环境）使用，用于迁移；不用于开发机直连拉生产 |
| db-tunnel | 仅保留给服务器侧受控维护命令；`dev.mjs` 不再启动中继，并强制 `loopback:5432/quant` |
| `SCHEDULER_DISABLED=1` | 不变 |

### 4.8 权限与网络隔离

| 层 | 设计 |
|----|------|
| 角色 | `quant_owner`：schema 所有者，跑 db:setup/DDL（容器内超级用户仅此角色）<br>`quant_app`：应用运行角色，`quant` schema 全量 DML（schema.sql 授权块赋权）<br>`quant_backup`：pg_dump 只读角色 |
| 网络 | `internal` 网络只挂 quant-db + quant-web（web 同时保留 default 出网）；quant-db 不映射任何端口 |
| 应用权限 | DATABASE_URL 用 `quant_app`，**不是超级用户**；schema.sql 末尾 REVOKE PUBLIC + 角色授权块（幂等，无角色时跳过） |
| 本机管理 | `docker compose exec quant-db psql -U quant_owner`（需进容器） |

### 4.9 Supabase 流量判断与配套优化

Supabase 官方：Free 5GB egress；Pro/Team 250GB included；Session/Supavisor Pooler 返回数据计入 Shared Pooler Egress。本项目确有每 5s 任务轮询 + 15s 调度 tick + 大量 AI 解读读取，5GB 易触顶，**自建库方向合理**。

但自建库只是把流量转成同机负载。**配套优化（独立小任务）**：
- 任务列表 5s 轮询 → 加条件请求（If-None-Match / 前端节流）或降频
- 列表接口不返回大字段（AI 解读 content 单独接口按需取）
- operation_logs / analysis_notes 分页 + LIMIT 已部分实现，核查调用侧

### 4.10 可选：web 启动时 DB 未就绪重试

无 depends_on 门禁后，若 DB 起得比 web 慢，首次请求可能报 schema 错误。可选在 `db.ts getDb()` 的 schema 校验失败路径加重试（指数退避 3 次）或在 compose 用 `depends_on` 启动顺序（非健康门禁）。默认不加，靠 pg 连接池超时 + 页面刷新即可；如需无缝可加。

### 4.11 密码轮换限制

当前项目规则禁止直接执行 `ALTER ROLE`，仓库也没有获批的角色密码轮换服务。因此本文不再提供任何
直接修改生产角色的命令。上线前使用独立强密码；需要轮换时，必须先建设并审批受控变更服务，再由
该服务完成权限校验、停写、审计和回滚。受控服务落地前，密码轮换属于明确的运维限制。

## 5. 风险与注意事项

| 风险 | 缓解 |
|------|------|
| 迁移期间快照不一致 | 4.3.1 停写窗口（停 quant-web = 停调度器 + web 写入） |
| db:setup/db:verify 验错库 | 全程显式 `-e DATABASE_URL` 指向 quant-db + `DATABASE_SSL_MODE=disable` |
| SSL 误判连不上 | `DATABASE_SSL_MODE=disable` / `LOCAL_SSL_MODE=disable` |
| 自动部署被 compose 破坏 | quant-db 在独立 override；主 compose 不变；三步发布（6.2） |
| 回滚被 quant-db 阻塞 | 无 depends_on 强依赖；DB 回滚用主 compose 单独启动 |
| 双调度器并发 | 单调度器约束（4.6），advisory lock 仅库内有效 |
| 备份缺失/不可恢复 | 每日 pg_dump + R2 保留 14 天 + **恢复演练（7.3）** |
| 应用超级用户权限过大 | quant_app 角色 + schema.sql 授权（4.8） |
| 自建库宕机 | restart: unless-stopped + healthcheck + 每日备份 + 回滚预案 B |
| 数据泄露 | 端口不暴露 + internal 网络 + 凭据不入库 + R2 凭据轮换 |

### 6.2 上线三步（原子维护窗口）

> **版本升级时机（硬约束）**：`SCHEMA_VERSION` 前向只增，代码与 schema 版本必须同时存在。
> 兼容 commit（本 PR）保持 v1；**schema.sql 授权块 + db.ts `SCHEMA_VERSION=2` 只能放在切换
> commit**，并在同一维护窗口内完成：停旧 Web → 用 v2 镜像对 quant-db 执行 `db:setup` → 迁移 → 切换。
> 绝不能把 v2 提前合入主分支——v2 代码连 v1 Supabase 会被 `validateSchema` 拒绝启动，旧代码
> 连 v2 库同理（评审 #2）。

**Step 1 — 兼容代码发布与切换前准备（仍为 v1）**

- 合并并自动部署本兼容 PR；确认线上仍是 `schema.sql v1 + SCHEMA_VERSION=1 + Supabase`
- **此时就安装新版** `docs/ops/deploy-quant.sh` 到 `/home/ubuntu/ops/deploy-quant.sh`，不要等到切换后
- `.env` 预置 `PG_OWNER_PASSWORD/PG_APP_PASSWORD/PG_BACKUP_PASSWORD`（强随机、分开，仅字母/数字/`_`）
- 给当前可工作的 v1 镜像保留不可变回滚标签：
  `docker image tag quant-web:latest quant-web:pre-cutover-v1`
- 在未合并的切换分支准备 v2 版本并完成代码审查；用该候选版本在非生产恢复目标完成 7.3
  恢复演练并记录 RTO；**恢复演练必须在最终停写迁移前完成**

**Step 2 — 暂停自动部署并准备 v2 镜像（生产仍由旧 v1 容器服务）**

1. 先在服务器 `.env` 设置 `DEPLOY_PAUSED=1`，再在同一个 SSH shell 等待获取维护锁；
   拿到锁即证明此前已在途的自动部署/备份已经结束。锁必须一直持有到 Step 3 完成：
   ```bash
   cd /opt/docker/quant/quant-python/quant-python
   exec 8>"$HOME/quant-maintenance.lock"
   flock -w 1800 8 || { echo "等待在途部署/备份超时，切换中止"; exit 1; }
   test "$(sed -n 's/^[[:space:]]*DEPLOY_PAUSED[[:space:]]*=[[:space:]]*\([^#[:space:]]*\).*/\1/p' ./.env | tail -n1)" = "1" \
     || { echo "DEPLOY_PAUSED 未设为 1，切换中止"; exit 1; }
   ```
2. 冻结并记录已审查、已演练的切换 commit SHA；其中 `schema.sql` 授权块与
   `db.ts SCHEMA_VERSION=2` 必须位于同一 commit。
3. 把该精确 SHA 推送到 master。GitHub Actions 可以触发，但服务器上的新版脚本会在 fetch/pull
   前因维护锁已占用或 `DEPLOY_PAUSED=1` 而退出。
4. 服务器手动执行：
   ```bash
   cd /opt/docker/quant/quant-python
   git fetch origin master
   git pull --ff-only origin master
   test "$(git rev-parse HEAD)" = "<已审核的切换 commit SHA>"
   cd quant-python
   docker compose -f docker-compose.oracle.yml -f docker-compose.oracle.db.yml build quant-web
   ```
   此时只是构建 v2 镜像，正在运行的旧 v1 容器不受影响。

**Step 3 — 停写、迁移并立即切换（同一维护窗口）**

1. 按 4.3.1 停止旧 `quant-web`，确认无运行中任务。
2. 按 4.3.2–4.3.5 执行：`quant-db --wait` → v2 `db:setup` → 受控同步 → `db:verify`。
3. 迁移验证通过后立即修改 `.env`：
   `DATABASE_URL=...@quant-db:5432/quant`、`DATABASE_SSL_MODE=disable`、`DB_MODE=selfhost`。
4. 启动已经构建并验证过的 v2，不在停写窗口重新构建：
   `docker compose -f docker-compose.oracle.yml -f docker-compose.oracle.db.yml up -d --no-build quant-web`
5. 页面抽查和 `db:verify` 均通过后，仍在维护锁内直接确认 `.env` 已是
   `DB_MODE=selfhost`，且叠加 DB override 的 `quant-web` 正在运行：
   ```bash
   test "$(sed -n 's/^[[:space:]]*DB_MODE[[:space:]]*=[[:space:]]*\([^#[:space:]]*\).*/\1/p' ./.env | tail -n1)" = "selfhost" \
     || { echo "DB_MODE 不是 selfhost，禁止结束切换窗口"; exit 1; }
   docker compose -f docker-compose.oracle.yml -f docker-compose.oracle.db.yml ps --status running quant-web \
     | grep -q quant-web || { echo "quant-web 未运行，禁止结束切换窗口"; exit 1; }
   ```
6. 把 `DEPLOY_PAUSED` 改为 `0`，执行 `flock -u 8` 释放维护锁；然后手动执行
   `/home/ubuntu/ops/deploy-quant.sh`，确认日志显示 `DB_MODE=selfhost` 且无待部署 commit。
7. 观察 1 周，Supabase 保留不删；业务必须提前接受 4.6 定义的回滚 RPO。

- **此后所有自动部署都走 DB_MODE=selfhost**（deploy-quant.sh 叠加 db override），否则下次发布
  quant-web 会丢失 internal 网络与 DATABASE_SSL_MODE=disable → 拿到指向 quant-db 的 URL 却
  无法解析且错误尝试 TLS（评审 Critical #2）。回滚时设回 `DB_MODE=legacy` 即可（配 Supabase URL）。
