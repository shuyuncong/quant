# 生产 500 排查步骤（2026-10-14）

现象：`https://quant.illsky.com` 全部路径 500，**包括静态资源与页面**。

> 注意：仓库 `public/` 里**没有 `logo.svg`**，它在正常状态下就返回 404，因此**不能当存活探针**；
存活探针请用 `/favicon.ico`（`src/app/favicon.ico`，正常 200）。


## 先看一个关键判别

静态资源也 500 —— 它在 Next.js 里是立刻返回的文件、**不碰数据库**。
所以这次**不是应用代码或数据库的连接时错误**，而是「没有进程在正常服务」：

- 要么 `quant-web` 容器没在跑 / 起不来（重启循环）
- 要么容器在跑但 Next 进程异常（内存耗尽、启动即崩）
- 要么 Nginx 连不上上游（容器在但端口没监听）

数据库挂掉**不会**让 `/favicon.ico` 这类静态资源变成 500。下面按这个顺序查。

> 注意：仓库 `public/` 里**没有 `logo.svg`**，它在正常状态下就返回 404，因此**不能当存活探针**；
存活探针请用 `/favicon.ico`（`src/app/favicon.ico`，正常 200）。

## 1. 容器状态（最先看这个）

```bash
docker compose -f docker-compose.oracle.yml -f docker-compose.oracle.db.yml ps
```

看三列的取值：

| 列 | 关注点 |
|---|---|
| `STATUS` | 是否 `Up`；出现 `Restarting` / `Exited (1)` 就是容器起不来 |
| `HEALTH` | 是否 `healthy`；`unhealthy` 说明 3111 的探活失败 |
| `PORTS` | 是否还有 `127.0.0.1:3111->3111/tcp` |

只列一条：

```bash
docker ps -a --filter name=quant-web --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'
```

## 2. 容器日志（**信息量最大的一步**）

```bash
docker logs --tail 200 quant-web
docker logs --tail 200 quant-db
```

重点找：

- `npm ci` / `npm error` / `package.json and package-lock.json are in sync`
  → 构建阶段失败（**本次我引入的 lockfile 问题就是这个**，已修复并推送）
- `Error: DATABASE_URL` / `ECONNREFUSED` / `password authentication failed`
  → 连接串或库凭据问题
- `validateSchema` / `schema version`
  → 代码与库的 schema 版本不匹配，应用会**拒绝启动**
- `JavaScript heap out of memory` / `Killed`
  → 内存不足（大字段那类问题会把内存顶满）
- 没有任何日志 + 立即退出 → 多半是构建/启动命令失败，看 `docker compose ... up` 的输出

## 3. 从容器内部直接打（绕开 Nginx）

```bash
docker exec quant-web node -e "fetch('http://127.0.0.1:3111/').then(r=>{console.log('HTTP',r.status);process.exit(0)}).catch(e=>{console.log('ERR',e.message);process.exit(1)})"
```

| 结果 | 含义 |
|---|---|
| `HTTP 200`/`307` | 应用是好的 → 问题在 Nginx 或 Cloudflare 一层，跳到第 6 步 |
| `ERR ...` | 应用没在监听 → 回第 2 步看日志 |
| 容器不在 | 回第 1 步，容器没起来 |

## 5. 数据库（只有在第 3 步返回 200 但业务接口失败时才需要）

```bash
docker exec -e DATABASE_URL="postgresql://quant_owner:${PG_OWNER_PASSWORD}@quant-db:5432/quant" \
  -e DATABASE_SSL_MODE=disable quant-web npm run db:verify
```

## 6. Nginx


→ 就是上游（3111）没在服务，和第 3 步的结论对上。

## 7. Cloudflare（本次另一个独立疑点）

我这边直接请求 `https://quant.illsky.com/logo.svg` 拿到的是
**403 + `Server: cloudflare` + `Server-Timing: cfOrigin;dur=0`**，
即 Cloudflare 自己的错误/质询页，`cfOrigin;dur=0` 表示**源站耗时 0ms = 根本没连上源站**。

要区分是"Cloudflare 拦了"还是"源站真的挂了"：

```bash
# 直连源站公网 IP（跳过 Cloudflare）
curl -sS -o /dev/null -w 'direct HTTP %{http_code}\n' -H 'Host: quant.illsky.com' http://<服务器公网IP>/
```

| 结果 | 含义 |
|---|---|
| 正常返回 | 源站是好的 → 问题在 Cloudflare（检查 DNS 是否被代理、WAF/速率限制规则、源站 IP 是否变了） |
| 也 500 | 源站确实有问题 → 以第 1~3 步为准 |

顺带看一眼最近的 Cloudflare 事件：Dashboard → 站点 → **Security Events / Analytics**，
确认是否有规则在拦；再确认 **DNS 记录指向的源站 IP 与服务器当前公网 IP 一致**
（Oracle 实例重建/IP 变更后 DNS 没更新，就会是这种「全站 500」的样子）。
