# 审计依赖哈希契约失修 —— 诊断与修复（2026-10-17）

## 一句话

`canonical_replay_semantics_audit` 的 9 个预登记常量**不是孤例**：
同一份"6-8 个依赖源码"的哈希表被**复制到 9 个审计脚本**里，值已实质漂移，
导致**这 9 个审计全部无法真实运行**；而**测试全绿**，因为测试都 monkeypatch 掉了常量。

## 复现（修复前）

```bash
cd quant-python/signal_system
python -m canonical_replay_semantics_audit
# RuntimeError: replay dependency hash mismatch: {...}
```

不是"需要参数"的问题 —— 8 个依赖里 **6 个**对不上。

## 根因一：登记口径混杂（三种）

逐个依赖追溯"登记值等于哪个提交的哪种行尾形态"：

| 依赖 | 登记值来源 | 形态 |
|---|---|---|
| `strategy_signal_policy` | `abff923`(2026-08-26) | **LF** |
| `strategy_market_gate` | `1b19aaf`(2026-08-26) | **LF** |
| `attribution_audit` | `e84aeb0`(2026-08-31) | **LF** |
| `candidate_integrity` | `cc33f13`(2026-09-02) | **LF** |
| `strategy_chan` | `c02418a`(2026-08-14) | **CRLF** ← Windows 产物 |
| `strategy_macd` | `abff923`(2026-08-26) | **CRLF** ← Windows 产物 |
| `backtest_winrate` | **无匹配** | **永久失联** |
| `utils_helpers` | **无匹配** | **永久失联** |

**"永久失联"的判定依据**：逐个修订扫描 + 7 种常见字节变换，均不匹配 ——

- `backtest_winrate`：全部 **14** 个历史修订，LF/CRLF 都不匹配；
- `utils_helpers`：全部 **18** 个历史修订，LF/CRLF 都不匹配，
  另加 BOM、CR-only、去尾空白等变换也不匹配。

→ 那两个值**并非本仓库历史中任何版本的产物**，无法追溯其原始锁定对象。

**结论**：2 个按 LF、2 个按 CRLF、2 个永久失联、2 个恰好与当前一致
（`market_gate` / `signal_policy`）。**不存在任何一个平台能让全部常量同时成立** ——
Windows 检出下"LF 的那几个"不匹配，Linux 检出下"CRLF 的那几个"不匹配。

## 根因二：机制上不可能自洽

```python
# candidate_integrity.py
def file_sha256(path: Path) -> str:
    return hashlib.sha256(path.read_bytes()).hexdigest()
```

`read_bytes()` 读**工作区原始字节** → 哈希取决于检出时的行尾。
只要登记值与比对值都用它，就必然带平台依赖。

## 根因三（最要紧）：测试从不校验真实值

`tests/test_canonical_replay_semantics_audit.py` 在 `:545` 起：

```python
monkeypatch.setattr(audit, "PREREGISTERED_CONFIG_SHA256", config_hash)   # 现场自造
monkeypatch.setattr(audit, "_dependency_contract", lambda *_: {...})      # 整个换掉
```

即**用现场自造的哈希替代真实常量，并把依赖校验整体替换** ——
于是"常量全错"这件事**没有任何测试会发现**。这也解释了为什么它能在 HEAD 上长期全绿。

## 修法

### 1. 新增共享单一事实来源：`audit_dependency_contract.py`

- `DEPENDENCY_PATHS`：12 个依赖源码的路径；
- `DEPENDENCY_EXPECTED_SHA256`：**唯一一份**登记值（附逐项来源注释）；
- `protected_sha256(path)`：源码按行尾归一、数据文件逐字节；
- `expected_for(names)`：缺名即 raise（fail closed）。

### 2. 哈希改为行尾无关

`candidate_integrity.source_text_sha256()`：`sha256(read_bytes().replace(b"\r\n", b"\n"))`。

**刻意不改 `file_sha256`** —— 它被 ~20 处复用，比对的是**数据文件**
（JSON/JSONL/pkl、历史清单、索引），归一化会改变内容与语义。
`protected_sha256` 按 `.py` 后缀分流，两类各取所需。

### 3. 9 个模块改为取用共享表

各模块内嵌的 dict 换成：

```python
DEPENDENCY_EXPECTED_SHA256 = {
    name: _SHARED_DEPENDENCY_EXPECTED_SHA256[name] for name in DEPENDENCY_PATHS
}
```

（别名导入，避免"同名自我赋值"。**注意不能写类型注解** ——
`DEPENDENCY_EXPECTED_SHA256: dict[str,str] = {name: DEPENDENCY_EXPECTED_SHA256[name] ...}`
会在赋值完成前求值右侧，直接 `NameError`。）

### 4. 补齐缺失的测试：`tests/test_audit_dependency_contract.py`（16 个用例）

补的正是此前**完全缺失**的那一环：

- `test_registered_hashes_match_real_files` —— **核心回归**：登记值必须等于真实文件哈希；
- `test_registered_hashes_are_line_ending_independent` —— 两个平台必须同值；
- `test_protected_sha256_normalizes_source_but_not_data` —— 分流正确；
- `test_consumer_module_derives_from_shared_contract`（9 个参数化）—— 消费方不得各自内嵌；
- `test_contract_detects_real_drift` —— **反向验证**：内容真变了必须报错；
- `test_expected_for_fails_closed_on_unknown_name` —— 缺名即 raise。

## 端到端实跑：审计已能真实运行

与本次修复无关；依赖契约校验发生在运行早期，已经通过。）

## 自指哈希的坑（本次踩到两次）

`candidate_integrity.py` 与 `canonical_replay_semantics_audit.py`
**都在自己的依赖契约里**，所以对它们的**任何**改动（包括 ruff 重新排序 import）
都会改变各自的登记值。本次因此更新了两轮。已在新测试里覆盖：
`test_registered_hashes_match_real_files` 会立刻报出这种漂移。

**顺序建议**：先 `ruff --fix` 全部改动文件，**再**重算登记值。
