# 行尾统一（LF）方案与实测结论

日期：2026-10-17
动机：`core.autocrlf=true` + 仓库存 LF → Windows 工作区是 CRLF、Mac 工作区是 LF，
同一个提交在两台机器上**字节不同**，导致按 `read_bytes()` 算 sha256 的冻结契约漂移
（已现症状：`volume_unit_continuity_audit` 的 `market_data_sha_match: False`）。

## 核心问题：修完会不会在 Windows 上又失效？

**答：不会 —— 前提是用 `eol=lf`，而不是只写 `text=auto`。** 两者行为不同，已实测。

| `.gitattributes` 写法 | 仓库存储 | Windows 检出 | 会再失效？ |
|---|---|---|---|
| （无，现状） | LF | **CRLF** | — |
| `* text=auto` | LF | **CRLF** ← **陷阱** | **会** |
| `* text=auto eol=lf` | LF | **LF** | **不会** |

### 实测 A：只有 `text=auto`（会失效）

本机 `core.autocrlf=true`，`.gitattributes` 写 `* text=auto`，检出后：

```
CR 数 = 3   （3 行全是 CRLF）
```

且 git 自己就打印警告：`LF will be replaced by CRLF the next time Git touches it`。
**这就是"修完又失效"的形态。**

### 实测 B：`eol=lf`（不失效）

```
检出后 CR 数 = 0   （纯 LF）
git status --porcelain  -> 无输出（干净）
```

**反复 checkout 三次：每次都 CR=0、status 干净** —— 恒定 LF，**不回潮**。

结论：**`eol=lf` 显式覆盖 `core.autocrlf`**（属性优先级高于该配置），
所以每台机器的 `autocrlf` 是 true 还是 false 都不影响结果。

### 额外的好消息：漂移会被 git 报出来

工作区被改成 CRLF 时，即使有 `eol=lf`，git **仍会标记为已修改**：

```
人为写入 CRLF -> git status --porcelain f.txt  =>  [ M f.txt]
```

**所以不会"悄悄漂移"** —— 有可见信号，且 `git checkout -- .` 能把它修回来（见下）。
（对比：如果没有 `.gitattributes`，CRLF 与 LF 在 git 看来都是"干净"的，
漂移完全无声 —— 这正是本会话踩坑的原因。）

## 修正：`--renormalize` 与 `checkout` 各自解决什么

> **更正**：本文初版写过"仅 `git checkout -- .` 无效"。**那句话对真实仓库不成立**，
> 它来自一个 blob 本身是 CRLF 的构造场景。真实仓库的 blob 已是 LF，
> 两种场景行为不同。以下为分组实测结论。

| 场景 | `git status` | `git checkout -- <file>` 的效果 |
|---|---|---|
| **blob 已 LF、工作区 CRLF**（**真实仓库的情形**） | ` M`（标记已改） | ✅ **重写为 LF（实测 CR=0）** |
| blob 本身含 CRLF（构造场景） | 需 `--renormalize` 才归一 | ⚠️ 单独用不足以归一内容 |

**对真实仓库的实际含义**：

- **`git checkout -- .` 是有效的**，能把工作区那批 CRLF 文本文件改写回 LF
- **`git add --renormalize .` 仍然需要**，但作用不是"修工作区"，
  而是**把仓库里本身就是 CRLF 的那 1 个 CSV blob 归一**（见下节）

## 风险盘点：`--renormalize` 会改内容的文件

扫全部已跟踪 blob（`git grep -l -P '\r' HEAD`，直读对象库、不检出），
**只有 3 个 blob 含 CR**：

| 文件 | 性质 | 归一化影响 |
|---|---|---|
| `docs/backtest-results/2026-10-07-.../metrics.csv` | **文本，31 行全 CRLF** | **内容会变**（CRLF→LF） |
| `docs/images/微信图片_20260902130012_115_10.jpg` | 二进制 | 被 `*.jpg binary` 保护，**不动** |
| `quant-python/web/src/app/favicon.ico` | 二进制 | 被 `*.ico binary` 保护，**不动** |

**其余全部已跟踪文件的 blob 都已是纯 LF** —— 对它们 `--renormalize` 不改变内容。

### 那个 CSV 安全吗？已实测

唯一读取它的是 `scale_out_take_profit_study.py:91`：

```
with (ARCHIVE_DIR / "metrics.csv").open(encoding="utf-8-sig", newline="") as handle:
    rows = [dict(zip(ARCHIVE_COLUMNS, row)) for row in csv.reader(handle) ...]
```

`csv.reader` 配 `newline=""` 是与行尾无关的。**实测两种行尾解析结果完全一致**：

```
CRLF(当前):   行数=30  首个键=('macd_zero_axis', 1)
LF(归一化后): 行数=30  首个键=('macd_zero_axis', 1)
```

**结论：该 CSV 归一化安全。**

## 正确步骤

```bash
# 0. 有未提交改动时先备份
git stash push -u -m "pre-lf-normalize"
```

```bash
# 1. 写 .gitattributes（binary 段是必需的，保护 png/jpg/ico/pkl）
printf '* text=auto eol=lf\n\n*.png binary\n*.jpg binary\n*.jpeg binary\n*.ico binary\n*.pkl binary\n*.gz binary\n*.pdf binary\n' > .gitattributes
```

```bash
# 2. 归一索引（把仓库里那个 CRLF 的 CSV 变成 LF）
git add --renormalize .
```

```bash
# 3. 确认只动了预期的文件（应只有 .gitattributes 与该 CSV）
git diff --cached --stat
```

```bash
# 4. 提交
git commit -m "chore: 统一行尾为 LF（.gitattributes eol=lf）"
```

```bash
# 5. 改写工作区（这一步能把现有 CRLF 文本文件变成 LF，已实测有效）
git checkout -- .
```

```bash
# 6. 两台机器都关掉自动转换（有 eol=lf 后已非必需，但减少困惑）
git config --global core.autocrlf false
```

## 之后要做的事：让哈希比对本身与行尾无关（**这才是真正的保险**）

`.gitattributes` 保证**检出**统一，但挡不住"某人的编辑器又写入 CRLF"。
既然 `git status` 会报出来，就不是隐患；但更稳的做法是让**比对逻辑本身**归一化：

在算 sha256 之前先把字节里的 `\r\n` 归一为 `\n`，再比对常量
（即此前建议的"**行尾归一 + 重登记**"）。这样：

- 无论工作区是 LF 还是 CRLF，测试都得出同一个哈希 → **不会再有平台差异**
- `.gitattributes` 负责让仓库一致，归一化负责让**测试**对行尾免疫，两者互补

受影响的冻结契约：

| 位置 | 机制 |
|---|---|
| `volume_unit_continuity_audit.py` | `EXPECTED_MARKET_DATA_SHA256`（**当前已红**，CRLF 形 `e5b8d396…` 与 LF 形 `530b37c9…` 都不匹配） |
| `backtest_winrate.py:591` | `hashlib.sha256(path.read_bytes())` 生成 `_qfq_history_manifest` |
| `backtest_winrate.py:743-780` | 逐行重算比对，不符 `ValueError("QFQ manifest row mismatch")` |

**顺序必须是"先统一行尾，再重登记"** —— 反了要登记两遍。
重登记按既定原则：**附登记注释，写明依据的字节形态（LF）与日期**，不改其它语义。

**注意**：`_qfq_history_manifest` 那两处比的是 **`.pkl` 数据文件**（不是源码），
它们是二进制、被 `*.pkl binary` 保护，**不受行尾影响**；
但**一旦重跑回测生成新 manifest，旧的冻结 manifest 会失效**
（此前已记录）——这与行尾是两件事，别混淆。
