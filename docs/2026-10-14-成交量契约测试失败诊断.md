# 成交量口径契约测试为何在 HEAD 就失败（诊断，未修）

日期：2026-10-14。**状态：已定位到根因，未做改动** —— 这是预登记契约，
改与不改需要决策，本文只给出证据与可选修法。

## 现象

```bash
python -m pytest quant-python/signal_system/tests/test_volume_unit_continuity_audit.py -q
# 1 failed, 36 passed
# RuntimeError: current volume interpretation contract failed:
#   {'config_sha_match': True, 'market_data_sha_match': False,
#    'volume_unit_shares_is_100': True, 'all_pass': False}
```

失败项只有 `market_data_sha_match`。**注意 `volume_unit_shares_is_100: True`** ——
成交量单位本身仍然是 100（股），契约的语义部分是通过的。

**且这是既有问题**：把本会话全部改动 stash 掉后仍然失败；`git status` 显示
`data/market_data.py` 与 `volume_unit_continuity_audit.py` 均未被本会话修改。

## 根因一：登记值落后两个提交

`EXPECTED_MARKET_DATA_SHA256 = 488f91c4…`，注释写着"2026-09-17 重新登记：
新增主源故障降级链（腾讯→东财→新浪）…"。逐个提交核对该文件的实际哈希：

| 提交 | 内容 hash（LF） | 说明 |
|---|---|---|
| `b7e5143` | `7cfbaf59…` | 更早 |
| `c1d519a` | `e1e52e40…` | 交易日历当日兜底 |
| `7835a04` | `f215eeb1…` / CRLF 形式 `488f91c4…` | **登记值来自这里** |
| `9d55e98` | `39f1bf1c…` | ← 现 HEAD 的该次改动 |
| 工作区 | `a2f3545e…`（CRLF） | |

`9d55e98`（"feat(quant): 重构分析、持仓、调度与本地回测"）对
`data/market_data.py` 只做了 **交易日历** 改动（8 增 5 删）：

```diff
-    def get_trade_dates(self) -> set[date]:
+    def get_trade_dates(self, strict: bool = False) -> set[date]:
```

**与成交量口径完全无关**，但文件的字节变了，而常量没有重新登记 —— 于是契约测试
开始失败，且没人注意。这正是"用整文件哈希当契约代理"的固有脆弱性：
任何无关改动都会击穿它。

## 根因二：`file_sha256` 依赖行尾（更严重）

```python
# candidate_integrity.py:37 / holdout_integrity.py:26
def file_sha256(path: Path) -> str:
    return hashlib.sha256(path.read_bytes()).hexdigest()
```

`read_bytes()` 读的是**工作区原始字节**，所以哈希值取决于检出时的行尾。实测本仓库
工作区的行尾是**混的**：

| 文件 | 工作区含 CRLF | 原始 hash | 归一 LF hash | 等于登记值？ |
|---|---|---|---|---|
| `config/config.yaml` | 否 | `d0be749e…` | 同左 | **是** |
| `data/market_data.py` | **是** | `a2f3545e…` | `39f1bf1c…` | **都不是** |

推论：**登记值 `488f91c4…` 是 `7835a04` 的 CRLF 形式**，
因此它只可能在"Windows 检出 + 恰好那个提交"下成立。生产与 CI 是 Linux（全 LF），
在那里即使回退到 `7835a04` 也**永远无法通过**。也就是说：

- 在 Linux：契约一直是红的（且没人跑它）；
- 在 Windows：只有行尾恰好匹配时才是绿的。

**一个恒定值不可能同时满足两个平台** —— 除非把哈希定义改成行尾无关。

## 可选修法（未执行）

| 方案 | 做法 | 风险 |
|---|---|---|
| **A 只重登记** | 把常量改成当前 LF 归一哈希 `39f1bf1c…`，附登记注释说明 `9d55e98` 只动了交易日历 | 低，但在 Windows 工作区（CRLF）仍会红 —— 治标不治本 |
| **B 行尾归一 + 重登记（推荐）** | 在**本审计内部**按 `read_bytes().replace(b"\r\n", b"\n")` 计算，再登记 `39f1bf1c…` | 中：语义更正确、跨平台一致；**不要动 `candidate_integrity.file_sha256`**，它被候选/留出集完整性清单复用，改它可能击穿其它已登记常量 |
| **C 收窄契约面** | 只对成交量相关函数体计算哈希，而不是整文件 | 高收益但工作量大：需要定义"成交量相关"的稳定边界 |

**建议 B**：改动局限在本审计内、跨平台一致、并保留"字节级锁定"的原意。

## 决策要点

1. 这不是本会话引入的，也不是生产运行问题 —— **成交量单位（100 股）依旧正确**，
   运行时行为不受影响；受影响的是"契约是否被机器强制"。
2. 不能直接删掉这个测试：它是成交量口径的唯一字节级锁定。
3. 若要修，**必须同时处理根因二的平台依赖**，否则修完在 Linux 上依然是红的。

## 同一批发现的第二处，而且它给出了关键证据

`canonical_replay_semantics_audit.py` 的两个常量，**登记约定并不一致**：

| 常量 | 对象 | HEAD 的 LF hash | HEAD 的 CRLF hash | 登记值命中 |
|---|---|---|---|---|
| `PREREGISTERED_MARKET_GATE_SHA256` = `fa69dbee…` | `strategy/market_gate.py` | `fa69dbee…` | `95c8b035…` | **LF ✓** |
| `PREREGISTERED_UTILS_HELPERS_SHA256` = `3ec75b77…` | `utils/helpers.py` | `4a224fad…` | `5618aa3d…` | **都不命中** |

两条结论：

1. **`market_gate.py` 的登记值是按 LF 算的** —— 也就是在 Linux/CI 上是对的，
   在 Windows 工作区（CRLF）反而"错"。所以这套契约**本来就是平台相关的**：
   同一个仓库，Windows 上红、Linux 上绿（或反之），取决于当初登记时用的是哪一边。
2. **`helpers.py` 的登记值既不是 HEAD 的 LF、也不是 HEAD 的 CRLF** ——
   我扫了改动该文件的最近 18 个提交，LF 与 CRLF 两种形式**都未命中**。
   也就是说这个常量**已经彻底失联**（登记对象在后续提交里被改过，常量没跟着更新），
   不是简单的行尾问题。

→ 因此**根因二（行尾依赖）是系统性的，根因一（登记落后）在此处是永久性的**。
两者叠加的结果是：这套"字节级锁定"契约目前**处于既不准确也不可移植的状态**。
真正要修的不是某几个常量，而是"哈希定义"本身（见下文方案 B）。
