# 机动现金配置核验：`position.mobile_cash_ratio` 到底是死配置还是被读？

核验日期：2026-10-14。范围：全仓库（Python 生产链路、回测、web/ TS 侧、config、schema、文档）。
方式：**调用图判据**（`file:line`），不接受 docstring 推断。本文只做审计，**未改动任何配置值或业务逻辑**。

---

## 〇、结论摘要（先给答案）

1. **`position.mobile_cash_ratio: 0.25` 不是"零读取"，但它读到的每一个值都只流向"信号建议文案/元数据"，
   没有任何一条路径把它变成下单股数或可用现金。** 生产下单链路（`monitor/service.py` 的三个
   `scan_*` 与 `TradeGate`）**完全不读它**。
   → 既有文档（`docs/2026-10-13-市场闸门核验.md:135`、`RUNBOOK.md:316`、`TODO.md:508`）里
   "全仓库只有写入没有读取"这句话**不准确**：应表述为"有读取，但读取结果不进任何真实资金计算"。
2. **`risk_control.position.reserve_cash_ratio` 才是真正的死键**：唯一写入点是
   `utils/helpers.py:354`（从 `mobile_cash_ratio` 拷贝），**全仓库 0 个读取点**。既有文档
   把"死"安在 `mobile_cash_ratio` 上，实际锅在这个下游拷贝键。
3. **"实测平均部署率 94.1%、61 天里 55 天满 4 仓"——精确出处不明（仓库内无产物可复现该数字），
   但口径可锁定为 2024-10-01~2024-12-31 的 61 个交易日、25 万本金、`max_positions=4`、
   `position_size_pct=0.25`**。同族 2024H1 归档（117 天）实测平均部署率 86.0%–95.7%、
   满仓 74–107/117 天，**量级与 94.1% 一致**。详见第四节。
4. **机制上"不留现金"是回测引擎的确定行为**：`research_backtest.py:517` 每个新仓
   `budget = min(cash, equity * 0.25)`——满 4 仓即用掉约 100% 权益，**不存在 25% 预留**。
   所以"文档说留 25%、实际几乎满仓"这个**结论成立**，只是理由要换成调用图证据。

## 二、调用图：为什么它"读了也没用"

**生产链路（会真正产生信号/落库/推送）不经过 `PositionManager`：**

- 生产扫描入口是 `quant-python/signal_system/monitor/service.py` 的
  `scan_zero_axis`（`service.py:842`）、`scan_yearline`（`:1319`）、`scan_macd_divergence`（`:1545`），
  经 `main.py:100` 与 `web_bridge.py` 调用。
- 这些文件**不 import** `core.router` / `strategy.strategy_engine` / `PositionManager`（已逐一 grep 确认）。
- 生产持仓闸门 `TradeGate`（`trading/positions.py:97`）读同一个 `config["position"]` 段，但只取
  `max_stocks`（`positions.py:342`）与 `max_position_per_stock`（`positions.py:355`），
  **从不取 `mobile_cash_ratio`**。

**`PositionManager` 只被两处构造：**
1. `quant-python/signal_system/strategy/strategy_engine.py:37`（日线扫描聚合引擎）。
2. 测试。

**而 `StrategyEngine` 只被"验收脚本 + 测试"构造**（无生产调用）：
- `quant-python/signal_system/acceptance/run_daily_scan_acceptance.py:284`
- `quant-python/backtest/acceptance/run_real_data_acceptance.py:597`
- `tests/core/strategy/test_strategy_engine_trend_signals.py:138`、`tests/integration/test_daily_scan_flow.py:143`

**结论（代码事实）：**
- `mobile_cash_ratio` 的读取结果只出现在信号的 `suggested_position_change` / `exposure_pct` 字段里
  （`strategies.py:103`、`t_trading.py:70/81/100/111/130/141`、`strategy_engine.py:608`）。
- 这些字段的**唯一非测试消费者**是：
  - 通知文案 `notifier.py:190/209/225`（"仓位变化建议"）——而
    `format_signal_report`/`build_daily_payload`/`send_daily_report`（`notifier.py:121/245/276`）
    **无生产调用者**（只有 `tests/integration/test_daily_scan_flow.py:151`）。
  - `bt_engine.py:234` 的下单比例——只有回测信号来自 `StrategyEngine` 时命中；生产回测走
    `research_backtest.py` 的 `position_size_pct` 与 `backtest_winrate.py` 的
    `base_position_per_stock`，**不读 `mobile_cash_ratio`**。
- 因此：**把它从 0.25 改成 0.5 或删掉，生产行为不变**（因为它连 `suggested_position_change` 都进不了生产）。
  这句是**代码事实**，依据是上面每个 `file:line` 的 import/调用关系。

> ⚠️ **推断（非事实）**：`t_trading.py` 的做T建议、`strategy_engine.py` 的减仓建议若未来被接进生产，
> `mobile_cash_ratio` 会立刻变成"影响建议仓位"的活配置。当前未接，是"尚未接线"，不是"设计上不需要"。

### 4.2 可复核的等价证据（同族 2024 归档，含逐日权益曲线）

我从仓库内**带 `equity_curve`** 的归档直接重算了"平均部署率 = mean((equity−cash)/equity)"与"满 4 仓天数"
（`docs/backtest-results/2026-10-07-three-strategies-stop-loss/comparison.json`，2024H1，117 天，250k，4 仓，25%）：

| 策略 / 止损档 | 平均部署率 | 满 4 仓天数 |
|---|---:|---:|
| 日线零轴金叉 @3% | 86.00% | 74/117 |
| 日线零轴金叉 @5% | 92.95% | 94/117 |
| 日线零轴金叉 @7% | 94.76% | 101/117 |
| 日线零轴金叉 @9% | 95.67% | 107/117 |
| 年线趋势 @3% | 87.24% | 75/117 |
| 零轴＋底背离 @6% | 57.87% | 29/117 |

**读法**：主策略（零轴金叉/年线趋势）在 2024H1 的平均部署率落在 **86%–95.7%**，**满 4 仓 74–107/117 天**。
这与"94.1%、55/61 满仓"**量级一致**，方向一致（几乎满仓、无 25% 预留）。

### 4.3 Q4 窗口的界内复核（重建，非直接产物）

2024-10-01~12-31 的归档 `comparison.json` **不含逐日权益曲线**（已被裁剪，仅剩 `metrics/trades`），
无法精确复算 `55/61`。用 `trades` 的进出场日 + 样本交易日历（61 天）重建：

- 直接用已平仓交易重建：满 4 仓 **38/61**、平均持仓 3.36 只（因 4 只期末未平仓的建仓日缺失，**低估**）。
- 补入"期末未平仓"的满仓路径后：日线零轴金叉/年线趋势均达 **61/61 满仓、部署率≈100%**。
- **判定**：`55/61` 落在 `38/61`（保守下界）与 `61/61`（含未平仓的乐观上界）之间，**与声称的 55 自洽**，
  但因缺原始权益曲线，**只能算"量级自洽"，不算"复核通过"**。

### 4.4 机制量化（为什么必然接近满仓）

`signal_system/research_backtest.py:517`：

```python
budget = min(cash, equity * allocation)   # allocation = position_size_pct = 0.25
```

每开一个新仓吃"当前权益的 25%"，4 个仓满仓时合计 ≈100% 权益，**没有任何一处分出 25% 留存现金**。
`backtest_winrate.py:4001` 同理（默认 `position.base_position_per_stock`）。
所以"把 `mobile_cash_ratio` 当已生效的现金闸门"在回测与生产上都是错的——这是**代码事实**。

## 六、两个方案的风险对比

### 方案 A：实现它（让"预留 25%"名副其实）

**要改什么**：新增"机动现金账户"语义——例如在 `research_backtest.py`/`backtest_winrate.py` 与
`TradeGate` 里按 `1 − mobile_cash_ratio` 限制总部署上限，或在日线扫描里把
`mobile_exposure_ratio()` 接进真实下单价。

**风险**：
1. **直接改变生产/回测仓位**：总部署上限从 ~100% 降到 ~75%，会改变所有历史对照结论的可比性
   （2026-10-07/10/12 三份归档全部作废口径对比）。
2. **必须重跑回测并做样本外验证**：`docs/学习/策略对照研究.md:1007` 已经实测"单笔低于 15% 纯属现金拖累"、
   "5 仓×25% 第 5 只买不满"；降低部署率极可能压低年化（4.2 表里止损越松部署越高、收益结构随之变化）。
3. **需要用户拍板**：这是仓位与风险敞口的语义变更，不是 bug 修复，**属于产品决策**。
4. 涉及至少 4 处引擎/闸门（`research_backtest.py`、`backtest_winrate.py`、`trading/positions.py`、
   可能的 `monitor/service.py`），**改动面大于看起来的样子**。

### 方案 B：删除它（从配置与文档里删掉）

**要改什么**：删 `config.yaml:201` 与 `:307` 两个键、`helpers.py:185/263/354`、
`position_manager.py:21/35/40`（连带 `base_exposure_ratio` 的 `(1−mobile_cash_ratio)` 项）、
`strategies.py:77/82`、`t_trading.py:59/119`、`strategy_engine.py:589/626`
（这些地方要么删、要么换成显式常量），以及 4 个测试 fixture。

**风险**：
1. **同样是"配置键删除"，需要用户确认**（任务硬约束：本轮不动配置）。
2. **会牵动 15 个读取点**（见 §1 表 #6–#16），其中 `base_exposure_ratio()` 的公式里
   `mobile_cash_ratio` 是**分母项**——删掉必须给 `target_stocks` 公式一个确定性替代
   （现默认 3 只 → `(1−0.25)/3 = 0.25` 恰好等于 `base_position_per_stock`，删掉后数值可能漂移）。
3. 若未来要做 `get_available_mobile_cash`（真实机动资金），删掉这个键会**丢掉唯一的需求锚点**
   （配置里再也没有"我打算留 25%"的声明）。
4. 硬编码常量会让"想改成留 30%"变成一个代码改动而不是配置改动。

### 方案对比小结

## 八、存疑点 / 证据不足处

1. **"94.1% / 55 of 61" 精确出处不明**：仓库内无产物可复现；口径可锁定（§4.1），
   量级可佐证（§4.2），但**精确数字不可复核**。若主线有该次会话的一次性脚本，需另找。
2. **Q4 精确复核受阻**：`docs/backtest-results/2026-10-12-.../comparison.json` 与
   `output/backtests/scale-out-take-profit-250k-2024q4/comparison.json` 均已裁剪掉 `equity_curve`
   （只剩 `metrics/trades/open_positions`），故只能区间重建（§4.3），**不能给出精确日均部署率**。
   全仓库**不存在**任何以 `2024-10` 开头的 `equity_curve`。
3. **"生产不读"的边界**：本文结论"生产链路不读 `mobile_cash_ratio`"基于
   `monitor/service.py` / `web_bridge.py` / `main.py` 的 import 与调用图。
   若存在**仓库外**的部署脚本（如 Oracle 上的独立 cron/服务）直接调用
   `StrategyEngine` 或 `core.router`，则 `mobile_cash_ratio` 会经 `suggested_position_change`
   间接影响其信号建议文案。**仓库内无此证据**，标记为存疑。
4. **`bt_engine.py:234` 的实际触发面**：它确实消费 `suggested_position_change`，
   但我只在 `backtest/acceptance/run_real_data_acceptance.py` 与回测单测里看到
   `StrategyEngine → bt_engine` 的串联，**未穷尽所有回测入口**。若有回测把 `core.router`
   的信号喂给 `bt_engine`，则该回测的**下单比例**会受 `mobile_cash_ratio` 影响。
5. **`position_manager.py:35` 的公式敏感性**：`base_exposure_ratio = min(0.25, (1−0.25)/3, 0.40) = 0.25`，
   `mobile_exposure_ratio = min(0.25, 0.40−0.25) = 0.15`。即**当前配置下"机动"实际只有 15%，不是 25%**——
   25% 被 `max_position_per_stock=0.40` 削掉了。所以即便将来"实现它"，语义也是 15% 而非 25%，
   这一点**文档从未说明**。
